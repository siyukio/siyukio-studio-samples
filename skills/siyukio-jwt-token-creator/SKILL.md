# siyukio-jwt-token-creator

## Overview

Implement a consistent JWT authorization workflow for Siyukio services. Generate access and refresh tokens, convert them to authorization strings, validate incoming authorization strings, and reject invalid or wrong-type tokens.

## Usage scenario: derive access token from refresh token

When a verified token has `refresh == true`, it can be used to generate its corresponding access token. The generated access token must keep the same `uid`, `name`, and `roles` as the refresh token, with token type switched to access (`refresh = false`).

Prefer this direct conversion when available:

```java
Token accessToken = refreshToken.createAccessToken();
String accessAuthorization = tokenProvider.createAuthorization(accessToken);
```

## Scope

Create or update code under:

```
{project-name}/{project-name}-{domain}/src/main/java/{package-path}/{domain}/application/
{project-name}/{project-name}-{domain}/src/main/java/{package-path}/{domain}/api/
```

Typical files:

- `application/*Service.java` for issue/refresh logic
- `api/*Controller.java` for login/refresh endpoints and token checks
- `api/dto/*Request.java` and `api/dto/*Response.java` for authorization payloads

## Required contract

Use these APIs exactly:

```java
@Autowired
private TokenProvider tokenProvider;
```

```java
String authorization = tokenProvider.createAuthorization(token);
Token token = tokenProvider.verifyToken(authorization);
```

Token definition:

- `io.github.siyukio.tools.api.token.Token`
- Fields: `id` (generated), `uid`, `name`, `roles`, `refresh`

Validation rule:

- `tokenProvider.verifyToken(authorization)` returns `null` means invalid authorization.

## Required rules

1. Always inject `TokenProvider` with `@Autowired` in classes that create or verify authorization.
2. Always convert `Token` to client-facing authorization by `tokenProvider.createAuthorization(token)`.
3. Always validate incoming authorization by `tokenProvider.verifyToken(authorization)`.
4. Treat `token == null` as invalid token and reject the request.
5. Treat `refresh = true` as refresh-token-only usage; never allow it for normal API access.
6. Treat `refresh = false` as access token usage.
7. Do not assign `id` manually; keep `id` generated by token implementation.

## Execution workflow

### 1) Normalize token claims

- `uid`: stable user identity
- `name`: display/account name
- `roles`: role list used by authorization logic
- `refresh`: token type flag (`false` for access, `true` for refresh)

### 2) Create authorization pair on login

Create two tokens from the same claims:

- access token with `refresh = false`
- refresh token with `refresh = true`

Convert both to authorization strings and return to client.

Template:

```java
private String createAuthorization(String uid, String name, List<String> roles, boolean refresh) {
    Token token = Token.builder()
            .uid(uid)
            .name(name)
            .roles(roles)
            .refresh(refresh)
            .build();
    return this.tokenProvider.createAuthorization(token);
}
```

```java
String accessAuthorization = createAuthorization(uid, name, roles, false);
String refreshAuthorization = createAuthorization(uid, name, roles, true);
```

If `Token.builder()` is unavailable, use the project's constructor/factory while keeping the same field semantics.

### 3) Refresh access token

For refresh endpoint:

1. Verify incoming refresh authorization string.
2. Reject when token is `null`.
3. Reject when `token.refresh() != true`.
4. Re-issue access token from verified claims (`uid`, `name`, `roles`) with `refresh = false`.
5. Prefer `token.createAccessToken()` when available; it should preserve `uid`, `name`, and `roles`.
6. Optionally rotate refresh token when project policy requires it.

Template:

```java
Token refreshToken = this.tokenProvider.verifyToken(request.refreshAuthorization());
if (refreshToken == null || !refreshToken.refresh()) {
    throw new ApiException("Invalid refresh authorization");
}

Token newAccessToken = refreshToken.createAccessToken();
String newAccessAuthorization = this.tokenProvider.createAuthorization(newAccessToken);
```

Fallback when `createAccessToken()` is unavailable:

```java
String newAccessAuthorization = createAuthorization(
        refreshToken.uid(),
        refreshToken.name(),
        refreshToken.roles(),
        false
);
```

### 4) Validate client authorization on protected APIs

For protected business APIs:

1. Verify authorization string.
2. Reject when token is `null`.
3. Reject when `token.refresh() == true` (refresh token is not an access token).
4. Continue with business logic using `uid` and `roles`.

Template:

```java
Token accessToken = this.tokenProvider.verifyToken(authorization);
if (accessToken == null || accessToken.refresh()) {
    throw new ApiException("Invalid authorization");
}

String uid = accessToken.uid();
List<String> roles = accessToken.roles();
```

### 5) Role-aware authorization checks

Use `token.roles()` to apply endpoint-specific access control, and keep role constants aligned with common role definitions in the project.

## Verification

From `{project-name}/` run:

```bash
./mvnw -pl {project-name}-{domain} -DskipTests compile
```

If tests exist for auth flows:

```bash
./mvnw -pl {project-name}-{domain} test -Dtest=*Auth*Test,*Token*Test,*Login*Test
```

Then confirm:

- Login or authorization-issue endpoint returns both access and refresh authorization strings when required.
- Refresh endpoint accepts only valid refresh authorization.
- Protected APIs reject `null` token and reject refresh token as access token.
- `verifyToken(...) == null` paths are fully handled without null-pointer behavior.
